1 · System overview

Two front-ends, one backend. A nine-year-old PHP booking site is being rebuilt as a single Django process that presents two UI surfaces plus a database:

  • Client Site — the client-facing Next.js app customers use to book. It runs in the browser and talks to Django's JSON REST API (/api/).
  • Back Office — the staff dashboard, rendered by Django's template engine (server-side HTML, no separate JS app) at /dashboard/. It replaced Django admin entirely.
  • MariaDB 10.11 — the application database, plus a read-only sanitised legacy replica the one-shot importers copy from (never used at runtime).

Both surfaces share the same models, auth and business rules — they differ only in how they render. The interactive maps for each live in §8.

6 · Client-site architecture (Next.js)

How the client site holds state, moves data, and authenticates. In one line: two state systems by concern — TanStack Query for server data, a Zustand global store for the booking wizard — talking to Django through a thin service layer over a cookie-authenticated fetch.

How state is managed

Directly answering “global provider / dispatcher?” — no Redux, no reducer/dispatch, no app-wide Context. State is split by concern into two purpose-built stores:

ConcernToolWhereShape
Server data (vehicles, pages, bookings, quotes)TanStack Query v5 providers/Providers.tsx — one QueryClientProvider useQuery/useMutation; cache w/ staleTime 60s, retry 1
Booking wizard (search → vehicle → extras → passenger → payment)Zustand — global store lib/booking/store.ts · useBookingStore module-level hook; direct set() setters + reset(); persist → sessionStorage["mm-booking"]
Cross-cutting React ContextReact Contextonly the Query client no custom auth/app Context provider
Auth / sessionhttpOnly cookieserver-set; no token in JS read current user via authService.me() wrapped in useQuery

Data flow

  1. A component calls a service (e.g. fleetService.listVehicles()), usually inside useQuery.
  2. The service picks mock or HTTP from USE_MOCKS (lib/api/config.ts) — no component change to switch.
  3. The HTTP impl calls the fetch client (lib/api/client.ts): credentials:"include", JSON, throws ApiRequestError on non-2xx, returns undefined on 204.
  4. Server responses are cached by TanStack Query; wizard selections are written to the Zustand store and persisted so a refresh mid-flow survives.

Authentication

  1. POST /api/auth/login/ {email, password} sent with credentials:"include".
  2. Django responds with the User and a Set-Cookie: mm_store_sessionid (httpOnly, SameSite=Lax, Secure in prod). The storefront session cookie is deliberately not the default sessionid — that name is reserved for the staff dashboard/admin, so a customer login on a shared host (all localhost in dev) can never clobber or 403 a staff session. See config.session.ScopedSessionMiddleware (cookie name chosen per path: /api/ → mm_store_sessionid, everything else → sessionid). The CSRF cookie is scoped the same way (ScopedCsrfMiddleware: /api/ → mm_store_csrftoken, else csrftoken) — otherwise a storefront login(), which rotates the CSRF token, would invalidate the token in an open dashboard/driver form. See Changelog (§13).
  3. Every later request auto-carries the cookie — no token handling in JS.
  4. GET /api/auth/me/ resolves the current user; wrap it in useQuery for app-wide auth state.
  5. POST /api/auth/logout/ clears the cookie server-side.
Two gaps to close during the rebuild (§10): the fetch client sends no X-CSRFToken header, so authenticated writes (booking, cancel) would 403; and there is no middleware.ts, so /booking/* and a future /account/* are not route-gated.

9 · Booking & pricing flow

The security spine of the rebuild: the client never sends a price. The server derives every fare, signs it into a short-lived token, and re-derives the total before charging.

1. Pick vehicle + trip ─▶ POST /api/quotes/ │ server: Google Distance Matrix → miles │ + DistanceBand rate + minimum_fare │ + TimeSurcharge / BlackoutDate % + tax ▼ 2. { quote_token (signed), price breakdown, TTL ~30 min } 3. POST /api/payments/intent/ ─▶ Stripe PaymentIntent (card → Stripe only) 4. POST /api/bookings/ { quote_token, passenger, payment ref } │ server re-validates token + re-derives total ▼ 5. Booking created (totals frozen) + BookingPriceLine rows + Payment ; confirmation
Why: the legacy PHP app carried the fare in $_SESSION and trusted it at payment. This design makes that tampering impossible — no field anywhere accepts a client-supplied price. Money is always a decimal string.

10 · Integration gap (resolved)

Closed 2026-09-26 — the client site now runs on the real backend. The price-carrying API layer was replaced (not adapted):
  • src/lib/api/ rewritten to the real paths (/api/vehicles/, /api/quotes/, …); the old /api/fleet/vehicles/ + client-side prices are gone.
  • The fetch client sends CSRF (X-CSRFToken from cookie), primed by GET /api/auth/csrf/.
  • The wizard is rewired around POST /api/quotes/ → quote_token → POST /api/bookings/; USE_MOCKS=false. Funnel verified end-to-end in Docker (real booking in the DB).

Remaining: Stripe test keys to enable card entry; login/register + marketing pages are still stubs. See the Changelog (§13) for the full record.

11 · Extending these docs

📌 Working rule — document as you build. Every feature, endpoint, or behaviour change to this app is recorded in these docs in the same task that ships it: update the relevant section (map status, endpoint reference, flow) and add a dated entry to the Changelog (§13). The docs are the source of truth for what exists; code is the source of truth for how. If it isn't written here, it isn't done.
⚠️ Porting gotcha — jQuery-plugin sections (recurring bug, now guarded). The Luxride template drives sections with jQuery plugins — slick sliders, Bootstrap accordion/dropdowns (data-bs-*), WOW reveals, Perfect Scrollbar — whose CSS is scoped to runtime-injected wrappers/classes (e.g. .list-how .slick-list .slick-track li h4{color:#fff}). Ported verbatim to React without the plugin, those selectors stop matching and the section silently breaks (invisible text, overflow, dead toggles). Rule when porting a page: (1) re-implement plugin behaviour with the React equivalent — Swiper for any slick/carousel; (2) data-bs-* toggles work via the Bootstrap bundle now loaded globally in app/layout.tsx; (3) otherwise add explicit overrides in public/assets/css/custom.css. Before shipping a page, grep it for slick · data-bs · perfect-scroll · magnific · count and handle each hit — never rely on the plugin's runtime markup.

These docs are built to grow. Everything is one self-contained HTML file with no build step or dependencies.

To change…Do this
Add a client page or back-office screen to the mapAdd an object to CLIENT_TREE or BACKOFFICE_TREE in the page script — {title, path, status, desc, api}. No layout code.
Add a whole new section/groupAdd a group {id, title, path, type, children:[…]}. type sets the accent (group/auth/wizard).
Add a third UI surface (e.g. a mobile app)Copy the tree shape into a new *_TREE const and add a tab that sets TREE and calls render();fit().
Update a funnel stepEdit the FLOW array.
Refresh the DB schema after a migrationRe-run the Django introspection snippet (see repo notes) and paste into §5.
Add a new doc pageReuse this file's <style> block as a shared design system; keep the sidebar-nav + numbered-sections pattern.

Convention: status is built or stub; paths are real routes; the map's card colour and the drawer read straight from the data, so the map can never drift from what you typed.
